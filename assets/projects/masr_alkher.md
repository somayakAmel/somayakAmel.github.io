## 1. Project Overview

Gharemeen is a Flutter mobile application (Android and iOS) built for field research teams conducting social and financial assessments of debt cases. It is an internal operational tool, not a consumer product — users are staff members of the operating organization, working across four distinct roles.

The app serves a role-based workflow. Field researchers are assigned cases, travel to conduct in-person household assessments, and complete multi-step research forms on-site. Quality administrators and quality supervisors review that work, assign cases down the hierarchy, and approve or reject submitted research. A super-admin role has broader access.

Role separation is enforced in code through a `UserType` enum (`fieldResearcher`, `qualityAdministrator`, `qualitySupervisor`, `superAdmin`), which drives both endpoint selection and available actions:

```dart
// lib/features/dashboard/presentation/cubit/dashboard_cubit.dart
url: switch (user?.type) {
  UserType.fieldResearcher      => Endpoints.fieldResearcherDashboard,
  UserType.qualityAdministrator => Endpoints.qualityAdminDashboard,
  UserType.qualitySupervisor    => Endpoints.qualitySupervisorDashboard,
  UserType.superAdmin || _      => Endpoints.dashboard,
},
```

The application is Arabic-first, with full right-to-left layout support throughout.

## 2. Problem

The core constraint driving this project's architecture is visible directly in the code: **field researchers conduct household assessments in locations without reliable internet connectivity.**

This creates several concrete problems:

1. **Data loss risk during fieldwork.** A researcher completes a lengthy multi-step assessment form in a household with no signal. Without offline persistence, that work is lost.

2. **Assessment forms are long and structured.** The family members module alone spans six sequential steps, each with its own data model (`family_member_step1_model.dart` through `family_member_step6_model.dart`) and its own API endpoint. Losing progress mid-form is expensive in field time.

3. **Case data must be readable offline.** A researcher arriving at a household needs to see the case details, prior research, and household composition — data that was fetched while they still had connectivity.

4. **Mutations made offline must eventually reach the server**, without duplicate submissions when connectivity returns intermittently.

5. **Multiple roles need different views of the same case data**, with assignment actions flowing down a hierarchy — and those assignment actions may also be performed offline.

## 3. Solution

The application is built as an **offline-first system** rather than an online app with caching bolted on. Three distinct mechanisms work together:

**A write-through read cache.** Every repository checks connectivity first. When online, it fetches from the API and mirrors the result into a local SQLite database. When offline, it reads from SQLite and applies filters locally. Cache-write failures are logged but never propagated, so a database problem cannot break a working network request:

```dart
// lib/features/cases/data/repository/case_repo_impl.dart
Future<(List<CaseModel>, int)> getAssignedCases(CaseSearchInputs? caseSearchInputs) async {
  if (await _networkInfo.isConnected) {
    final result = await _caseRemoteDatasource.getAssignedCases(caseSearchInputs);
    try {
      await _caseLocalDatasource.updateAssignedCases(result.$1);
    } on Exception catch (e) {
      e.dLog("data base error :: ");
    }
    return result;
  } else {
    final localCases = await _caseLocalDatasource.getAssignedCases(caseSearchInputs);
    return (localCases, 1);
  }
}
```

**An offline write queue.** Mutations performed without connectivity are serialized into `SharedPreferences` as a timestamped, FIFO-ordered queue. Requests are de-duplicated by operation type plus entity ID, so repeatedly saving the same form step replaces the pending entry rather than stacking duplicates:

```dart
// lib/features/family_members/data/services/family_members_offline_queue_service.dart
Future<void> queueRequest(QueuedFamilyMemberRequest request) async {
  final queue = await _getQueue();
  queue.removeWhere((existing) =>
      existing.type == request.type &&
      existing.paramsJson['caseId'] == request.paramsJson['caseId']);
  queue.add(request);
  await _saveQueue(queue);
}
```

**A replay-on-reconnect sync service.** When connectivity returns, sync services drain the queue and report per-item outcomes back to the user in Arabic, so a researcher knows exactly which steps uploaded and which failed:

```dart
// lib/features/family_members/data/services/family_members_sync_service.dart
Future<(int, List<String>?)> syncQueuedRequests() async {
  if (!await _networkInfo.isConnected) return (0, null);
  final queuedRequests = await _localDatasource.getQueuedRequests();
  if (queuedRequests.isEmpty) return (0, null);

  int successCount = 0;
  List<String> messages = [];
  for (final request in queuedRequests) {
    try {
      await _syncSingleRequest(request);
      await _localDatasource.removeQueuedRequest(request.id);
      successCount++;
      messages.add('تم رفع ${getStepName(request.type)} للحالة ${request.paramsJson['caseId']} بنجاح.');
    } catch (e) {
      await _localDatasource.removeQueuedRequest(request.id);
      messages.add('فشل رفع ${getStepName(request.type)} للحالة ${request.paramsJson['caseId']}.\n السبب: $e');
    }
  }
  return (queuedRequests.length, messages.isNotEmpty ? messages : null);
}
```

Repositories that support offline writes return a user-facing message describing what actually happened, so the UI can distinguish "saved to server" from "saved locally, will upload later":

```dart
// lib/features/social_research/data/repositories/social_research_repo_impl.dart
if (await _networkInfo.isConnected) {
  await _socialResearchRemoteDataSource.editSocialResearchForm(inputs);
  return "تم تعديل بيانات البحث الاجتماعي بنجاح.";
} else {
  await _socialResearchLocalDatasource.saveSocialResearchFormInputs(inputs);
  return "تم حفظ بيانات البحث الاجتماعي مؤقتًا حتى يتوفر اتصال بالإنترنت.";
}
```

## 6. Technical Highlights

### Monorepo with a strict package dependency ladder

The project is structured as a host application plus four local path-dependency packages, forming an acyclic dependency graph:

```
        lib/ (application)
         │      │       │
         ▼      ▼       ▼
  core_package  utils_package  locale_package
         │              │             │
         └──────────────┴─────────────┘
                        ▼
                  types_package
```

`types_package` contains only contracts — `ApiConsumer`, `CacheConsumer`, `AppInterceptors`, `BaseUseCase`, and the failure/exception hierarchies — with zero implementation. `core_package` implements them. This means swapping the HTTP client would require changing exactly one class (`DioConsumer`), because no code outside that package references Dio directly.

### DI-framework-agnostic packages

Packages never import `get_it`. Instead, they receive a registration function as a parameter:

```dart
// packages/core_package/lib/src/service_locator.dart
Future<void> initCorePackage(
  Function<T extends Object>(T object) register,
  sl,
  String baseUrl, {
  required dynamic Function(DioException) handelDioError,
}) async {
  final sharedPreferences = await SharedPreferences.getInstance();
  register<SharedPreferences>(sharedPreferences);
  register<CacheConsumer>(CacheConsumerImpl(sharedPreferences: sl<SharedPreferences>()));
  register<ApiConsumer>(DioConsumer(
    dio: sl<Dio>(),
    handelDioError: handelDioError,   // app-specific policy injected, not imported
    baseUrl: baseUrl,
    appInterceptors: sl<AppInterceptors>(),
    logInterceptors: sl<LogInterceptor>(),
  ));
}
```

App-specific policy — base URL, error handler, default language — is passed in rather than hard-coded, keeping the packages reusable across applications.

### `CustomState<T>` — a single state primitive

Rather than defining sealed state classes per operation, the project uses one generic status wrapper with a private constructor and `const` named factories, making invalid states unconstructable:

```dart
// lib/src/widgets/custom_state.dart
class CustomState<T> {
  final Status status;
  final T? data;
  final String? error;

  const CustomState._({required this.status, this.data, this.error});

  const CustomState.initial() : this._(status: Status.initial);
  const CustomState.loading() : this._(status: Status.loading);
  const CustomState.loadingWithClear() : this._(status: Status.loading, data: null);
  const CustomState.success(T data) : this._(status: Status.success, data: data);
  const CustomState.failure(String error) : this._(status: Status.failure, error: error);

  bool get isLoading => status == Status.loading;
  bool get isSuccess => status == Status.success;
  bool get isFailure => status == Status.failure;
}
```

The `loadingWithClear()` variant exists for a specific reason: plain `loading()` preserves previously-held data (enabling pagination to keep rendering the existing list while the next page loads), while `loadingWithClear()` explicitly drops it for offline refreshes where showing stale data during a reload would be wrong.

A cubit's state then holds one `CustomState<T>` per async operation, with field names mirroring method names:

```dart
class CasesState extends Equatable {
  final CustomState<(List<CaseModel>, int)> getAssignedCasesState;
  final CustomState<(List<CaseStatementModel>, int)> getCaseStatements;
  // ...
}
```

### Dart 3 records for compound returns

Paginated results flow as `(List<T>, int)` — items and total pages — unchanged from datasource through repository and use case into state, avoiding a wrapper class per endpoint. Records also carry "result plus message" pairs: `(List<FamilyMemberStep1Model>?, String?)`.

### Two-chokepoint error pipeline

All error handling funnels through exactly two functions. `handelDioError` translates `DioException` into typed exceptions, checking network-level failures *before* the status-code switch so offline errors aren't misclassified as server errors:

```dart
if (error.type == DioExceptionType.connectionError ||
    error.type == DioExceptionType.unknown ||
    error.error is SocketException ||
    error.error is HandshakeException) {
  throw const NoInternetConnectionException('لا يوجد اتصال بالانترنت');
}
```

`tryCatch` then converts exceptions into `Either<Failure, T>`, with a crash-reporting hook decoupled from any specific SDK and a testing bypass:

```dart
Future<Either<Failure, T>> tryCatch<T>({
  required Future<T> Function() tryFunction,
  bool isLogin = false,
}) async {
  try {
    return Right(await tryFunction());
  } on ServerException catch (e, stack) {
    if (!TestingEnvironment.isTesting) Completer().completeError(e, stack);
    if (e.toString() == 'Canceled') return Left(CancelFailure(e.message));
    else if (e is UnauthorizedException && !isLogin) { /* force re-login */ }
    return Left(ServerFailure(e.message));
  } on CacheException catch (e, stack) { /* ... */ }
  catch (e, stack) { /* ... */ }
}
```

The `isLogin` flag prevents the auth-redirect from firing during login itself — a wrong password shouldn't bounce the user off the login screen.

### Interceptor-driven authentication

No datasource, repository, or cubit ever passes a token. The interceptor reads it from cache on every request, so login and logout take effect immediately with no re-wiring:

```dart
options.headers.addAll({
  'Accept-Language': sl<LocaleCubit>().getLocale().languageCode,
  if (user != null) 'Authorization': 'Bearer ${user.token}',
  'Accept': 'application/json',
});
```

Session expiry is handled globally: a 401 triggers navigation to login via a static `GlobalKey<NavigatorState>` on `MyApp`, except when the failing request *is* the login call.

### Two-tier connectivity detection

`NetworkInfo` provides an imperative boolean check used by repositories. `NetworkConnectivityCubit` provides a reactive stream for UI banners — and notably does not trust the OS connectivity flag alone, validating real internet access by hitting a known endpoint with a DNS-lookup fallback, then scheduling periodic reconnect probes while offline:

```dart
final uri = Uri.parse('https://clients3.google.com/generate_204');
final res = await req.close().timeout(timeout);
final ok = res.statusCode == 204 || res.statusCode == 200;
```

This matters in the field, where a device can be attached to a captive-portal Wi-Fi that reports "connected" but passes no traffic.

### Dual-shape model serialization

Because the same models are persisted to SQLite *and* parsed from the API, `fromJson` handles both shapes — nested objects from the API and JSON-encoded string columns from the database:

```dart
details: CaseDetailsModel.fromJson(
    json['details'] is String ? jsonDecode(json['details']) : json['details']),
```

`toJson` correspondingly encodes nested objects into flat columns and adds derived sort keys (`received_at_ts`) that SQLite can order by.

### Localization with a debug-time safety net

Translations are loaded from runtime JSON assets rather than generated `.arb` files. A missing key renders loudly in debug and falls back silently in release:

```dart
extension LocaleExtension on String {
  String tr(BuildContext context) =>
      AppLocalizations.of(context)!.translate(this) ??
      (kReleaseMode ? this : 'Error : not found $this');
}
```

### Extension-based layout DSL

Layout code is written through extensions that make every dimension responsive and RTL-correct by construction:

```dart
Column(children: [
  AppSize.s16.spaceH,
  CustomText(title, fontSize: FontSize.f18),
]).withPadding(PaddingValues.p20.pSymmetricH)
```

All padding extensions return `EdgeInsetsDirectional` and all border extensions return `BorderRadiusDirectional`, so directional correctness is not something a developer can forget — it is the only option available.

## 7. Challenges

### 7.1 Preserving multi-step form work without connectivity
A six-step assessment form completed in a household with no signal represents substantial field time. Losing it is unacceptable, but naïvely retrying on reconnect risks duplicate submissions.

### 7.2 Making search and filtering work identically online and offline
The API supports server-side search, date-range filtering, and governorate filtering. Offline, the same UI must behave the same way against SQLite.

### 7.3 Inconsistent backend response shapes
Model parsing code shows extensive defensive handling, indicating the API returns the same logical field in different shapes across endpoints — nested objects in some responses, flattened fields in others, integers where booleans are expected, and the string `"null"` for absent values.

### 7.4 Persisting nested object graphs in a relational store
`CaseModel` contains nested `CaseDetailsModel`, `SocialResearchFormModel`, `FamilyMembersFormInputs`, `SocialSearchInfo`, and two `CaseUserModel` fields — a graph that does not map cleanly onto flat SQLite rows.

### 7.5 Sorting by date when timestamps arrive in multiple formats
The `normalize` function in `case_local_datasource.dart` handles at least two distinct date orderings, and `CaseModel._parseReceivedAtToMillis` has fallback parsing — indicating `received_at` is not consistently formatted.

### 7.6 Detecting genuine connectivity, not just network attachment
A device attached to Wi-Fi is not necessarily online.

### 7.7 Role-based behavior across four user types
Assignment targets, available actions, and dashboard endpoints all vary by role.

### 7.8 Schema evolution during active development
The SQLite database reached version 15, indicating repeated schema changes while the app was in use.

## 8. Solutions

### 8.1 → Queue with de-duplication and FIFO replay
Each form step is serialized with its parameters and a timestamp into `SharedPreferences`. De-duplication by `(type, caseId)` means saving step 3 twice replaces the pending entry rather than queuing two submissions. On reconnect, the sync service replays in timestamp order and removes each entry after processing. Synced requests are flagged with `offlineFlag: 1` so the backend can distinguish deferred submissions from live ones:

```dart
params = params.copyWith(offlineFlag: 1);
return await _remoteDatasource.postFamilyMembersStep1(params);
```

### 8.2 → Mirrored filter logic in the local datasource
The local datasource implements the same filter semantics against cached models, with the repository choosing the path:

```dart
bool filterCase(CaseSearchInputs caseSearchInputs, CaseModel caseModel) {
  final matchesSearch = input == null ||
      caseModel.idNumber.contains(input) || caseModel.name.contains(input);
  final matchesDate = (fromDate == null && toDate == null) ||
      (fromDate != null && toDate != null &&
       !receivedAt.isBefore(fromDate) && !receivedAt.isAfter(toDate));
  final matchesGovernorate = governorateId == null || caseModel.governorate.id == governorateId;
  return matchesSearch && matchesDate && matchesGovernorate;
}
```

The code is honest about a limitation: for case statements, governorate arrives as a string rather than an ID, so governorate filtering is explicitly skipped offline, with a comment stating why.

### 8.3 → Defensive parsing at the model boundary
Rather than scattering null checks through the UI, all shape tolerance is concentrated in `fromJson`:

```dart
governorate: json['governorate'] == null
    ? SimpleLookupItem(id: json['governorate_id'].toString(), name: json['governorate_name'])
    : SimpleLookupItem.fromJson(json['governorate']),

socialSearchInfo: (json['socialSearchInfo'] == null ||
        json['socialSearchInfo'] == '' ||
        (json['socialSearchInfo'] is String &&
         (json['socialSearchInfo'] as String).toLowerCase() == 'null'))
    ? null
    : SocialSearchInfo.fromJson(/* ... */),
```

### 8.4 → JSON-encoded columns with symmetric round-trip
Nested objects are `jsonEncode`d into TEXT columns on write and detected-and-decoded on read, letting one model class serve both the API and the database without a separate persistence model.

### 8.5 → Normalization plus a derived sort column
`normalize` rewrites both known date orderings into ISO-8601 before parsing, and `toJson` writes a precomputed `received_at_ts` epoch-milliseconds column so SQLite sorts numerically rather than lexically:

```dart
final result = await _dbHelper.getItems(table, orderBy: 'received_at_ts DESC');
```

### 8.6 → Active internet verification with fallback
`NetworkConnectivityCubit` issues an HTTP request to a known 204 endpoint, falls back to a DNS lookup, and — while offline — polls every 8 seconds until real connectivity is confirmed. The subscription and timer are both cancelled in an overridden `close()`.

### 8.7 → Role branching in the repository, not the UI
Assignment logic lives in `AssignUserRepoImpl`, so screens remain role-agnostic:

```dart
final UserType userRole = user!.type;
if (userRole == UserType.qualitySupervisor) {
  return await _assignUserRemoteDataSource.assignQualityAdmin(caseId, userId);
} else {
  return await _assignUserRemoteDataSource.assignFieldResearcherOrCurrentUser(caseId, userId);
}
```

### 8.8 → Versioned schema with an upgrade hook
`DatabaseHelper` uses `openDatabase(version: 15, onCreate: _createDB, onUpgrade: _onUpgrade)`, with table creation delegated to per-table classes (`CaseTable`, `AssignedCaseTable`, `GovernorateTable`, `SocialResearchFormTable`).

> **Needs confirmation:** the `_onUpgrade` implementation is currently an empty conditional block, so migrations appear to have been handled by reinstall during development rather than by in-place migration. Whether production users were migrated is not determinable from the repository.

## 9. Architecture Decisions

### Decision 1 — Cubit only, no Bloc with events

**Decision:** Every state holder extends `Cubit<T>`. No `Bloc`, no event classes.
**Reason:** The app's interactions are direct method calls from UI to state holder. Event classes would add a class per interaction with no added capability — there is no event sourcing, replay, or transformation requirement.
**Benefit:** Roughly one fewer class per operation; call sites read as `CasesCubit.get(context).getAssignedCases(inputs)`.

### Decision 2 — Repositories throw; use cases convert to `Either`

**Decision:** Repository methods return raw values or throw. Only use cases return `Either<Failure, T>`, and their entire body is a `tryCatch` wrapper.
**Reason:** Placing conversion in every repository method would duplicate error policy across dozens of methods.
**Benefit:** Error policy lives in exactly one function. Repositories stay readable and focused on the online/offline decision.

```dart
class GetAssignedCasesUsecase extends BaseUseCase<(List<CaseModel>, int), CaseSearchInputs> {
  final CaseRepo caseRepo;
  GetAssignedCasesUsecase(this.caseRepo);

  @override
  Future<Either<Failure, (List<CaseModel>, int)>> call(CaseSearchInputs params) async {
    return await tryCatch(tryFunction: () => caseRepo.getAssignedCases(params));
  }
}
```

### Decision 3 — Online/offline decision belongs to the repository

**Decision:** `NetworkInfo.isConnected` is checked in the repository, never in the cubit or datasource.
**Reason:** It is a data-sourcing concern. Putting it in the cubit would leak infrastructure into presentation; putting it in the datasource would mean each datasource knows about the other.
**Benefit:** Cubits are identical whether or not a feature supports offline. Adding offline support to a feature touches one file.

### Decision 4 — Cubits as factories, everything else as lazy singletons

**Decision:** `registerFactory` for cubits, `registerLazySingleton` for datasources, repositories, use cases, services, and DAOs.
**Reason:** A singleton cubit would retain state between screen visits — a stale list or a lingering error. Stateless collaborators have no such issue and benefit from single construction.
**Benefit:** Each screen gets clean state; `BlocProvider` disposes it on unmount.

### Decision 5 — Contracts in a dependency-free package

**Decision:** `types_package` holds only abstract classes and error types, depending on nothing internal.
**Reason:** It establishes a stable base that every other package and the app can depend on without creating cycles.
**Benefit:** Implementations are swappable. The entire app codes against `ApiConsumer`, so the HTTP client is a single-class change.

### Decision 6 — Hand-written serialization, no code generation

**Decision:** No `json_serializable`, no `freezed`, no `build_runner` anywhere.
**Reason:** Models must tolerate two input shapes (API JSON and SQLite rows) with per-field defensive logic that generated code cannot express.
**Benefit:** Full control over parsing edge cases; no build step; no generated files in review.
**Trade-off:** More boilerplate and more surface for manual error.

### Decision 7 — Runtime JSON localization instead of generated ARB

**Decision:** Translations load from `lang/*.json` at runtime via a custom `AppLocalizations`.
**Reason:** Avoids a code-generation step and allows translation files to be edited without rebuilding.
**Benefit:** Simple mental model; missing keys surface loudly in debug and degrade gracefully in release.
**Trade-off:** No compile-time key checking — a typo is caught at runtime, not build time.

### Decision 8 — Design tokens as static constants, not `ThemeExtension`

**Decision:** Colors, sizes, paddings, and radii are `static const` members on manager classes, read directly by widgets. `ThemeData` is minimal.
**Reason:** Avoids `context` lookups for values that never change at runtime (the app has no dark mode or theme switching).
**Benefit:** Compile-time constants, no `BuildContext` dependency, direct access. A role-alias layer (`primaryButtonBackground` → `primaryColor`) allows re-skinning without touching widgets.
**Trade-off:** Adding a second theme would require significant rework.

### Decision 9 — Imperative named routing

**Decision:** `onGenerateRoute` with a switch table; route names as `static const String` on each screen; typed argument classes cast once.
**Reason:** The navigation graph is shallow and mostly linear.
**Benefit:** Route names stay next to the widgets they name; a global `navigatorKey` enables navigation from the interceptor for session expiry.
**Trade-off:** No deep linking or URL-based navigation.

## 12. Lessons Learned

**Offline-first is an architectural stance, not a feature.** The decision to place the connectivity check in the repository — rather than in cubits or datasources — is what allowed offline support to be added feature-by-feature without touching presentation code. Retrofitting this onto an online-first design would have meant rewriting every cubit.

**Centralizing error policy pays compounding returns.** With `handelDioError` and `tryCatch` as the only two places errors are translated, adding a new error type or changing 401 behavior is a single-file change. Every use case in the codebase is a one-line `tryCatch` wrapper as a direct consequence.

**Abstractions justify themselves at the seams.** `ApiConsumer` and `CacheConsumer` initially look like ceremony over Dio and SharedPreferences. Their value showed up when the same models needed to serve both an HTTP API and a SQLite cache — the boundary already existed, so dual-shape parsing was a model-level concern rather than an architectural one.

**Constraining the API prevents whole error classes.** Because every padding extension returns `EdgeInsetsDirectional` and every border extension returns `BorderRadiusDirectional`, RTL correctness is not something a developer can forget — the non-directional option is simply not available in the DSL. Designing the toolkit so the correct thing is the *only* easy thing proved more reliable than code review.

**Defensive parsing belongs at the boundary.** Concentrating all backend inconsistency handling in `fromJson` factories kept null-checks and type-coercion out of repositories, cubits, and widgets. When a response shape changed, exactly one file needed attention.

**Untested code is a compounding liability.** This project has zero tests despite an architecture explicitly designed for testability — every dependency is an interface, and `TestingEnvironment.isTesting` was built into `tryCatch` from the start specifically to support testing. The infrastructure was laid and never used. Every refactor in the six-month history was verified manually. This is the clearest improvement I would make with the time again: the cost of writing repository and cubit tests would have been low precisely *because* the architecture supports them.

**Security defaults need explicit review before release.** The codebase contains a global `HttpOverrides` that accepts all TLS certificates (`badCertificateCallback => true`), unguarded by `kDebugMode`. Development conveniences like this need a tracked path to removal, not just an intention to remove them later.

**Shared internal packages need clear ownership boundaries.** Integrating four company packages accelerated delivery substantially, but modifications made to `utils_package` inside this repository create a divergence question — whether those changes flow back upstream, and how other consuming apps receive them. This is a coordination problem that package extraction creates and does not solve.
